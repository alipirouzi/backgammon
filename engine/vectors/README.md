# Engine test vectors

Machine-checked fixtures shared by the Rust test suite and the bindings'
parity tests (spec section 4.6 and 7). They are **generated, never edited by
hand**: `bg-core/tests/vectors.rs` and `bg-bot/tests/vectors.rs` fail when a
committed file differs from the generator's output, so any change to the
engine that alters them is visible in review as a diff of this directory.

| File | Generated by | Consumed by |
|---|---|---|
| `plays.json` | `cargo run -p bg-core --example gen_vectors -- plays vectors/plays.json` (run inside `engine/`) | `bg-core/tests/vectors.rs`; WASM and native parity tests `(planned)` |
| `decisions.json` | `cargo run --release -p bg-bot --example gen_decisions -- decisions vectors/decisions.json` (run inside `engine/`) | `bg-bot/tests/vectors.rs`; WASM and native parity tests `(planned)` |

## `plays.json`

A JSON array of 141 entries:

```jsonc
{
  "board": { "white": [0, …, 0], "black": [0, …, 0] },  // absolute board: index 0 = bar, 1..24 = points, 25 = off
  "onRoll": "white",                                     // "white" | "black"
  "dice": { "hi": 6, "lo": 3 },                          // hi >= lo
  "plays": ["24/18 13/10", "24/15", …]                    // every legal play, as notation relative to onRoll
}
```

- Entries 0–20: the opening position, White on roll, one entry per distinct
  roll in `Dice::all()` order (1-1, 2-1, 2-2, 3-1, 3-2, 3-3, …, 6-6).
- Entries 21–140: 40 positions × 3 rolls each. The positions are sampled
  along one continuous random walk (seed `0x5EED_2026_0903`, every ply rolls
  with `DiceRng` and picks a legal play at random; sides alternate from
  White; 1–9 plies between samples; the walk restarts from the opening when a
  game ends). Three consecutive entries share `board` and `onRoll`.
- `plays` lists exactly the output of `bg_core::moves::legal_plays` for the
  position as seen by `onRoll`, in the engine's order (one canonical play per
  resulting position, moves sorted by `from` descending then `to`
  descending, plays sorted by that key). Notation follows the engine's
  `Display for Play` (`bar/`, `/off`, `*` for a hit, `13/7(2)` collapsing).
- A position with no legal move yields `[""]`: the single empty play.

A consumer is correct when, for every entry, `legalPlays(board, onRoll, dice)`
returns the same list of notations in the same order.

## `decisions.json`

A JSON array of 30 entries, one bot decision each:

```jsonc
{
  "board": { "white": [0, …, 0], "black": [0, …, 0] },  // absolute board, as in plays.json
  "onRoll": "white",
  "dice": { "hi": 4, "lo": 3 },
  "match": {                                             // bg_bot::MatchContext from onRoll's point of view
    "length": 0, "myAway": 0, "theirAway": 0,            // length 0 = money game
    "crawford": false, "postCrawford": false,
    "cube": 1, "cubeOwnerIsMe": null                      // true | false | null (centred)
  },
  "level": "club",                                       // "beginner" | "intermediate" | "club"
  "seed": 12,                                            // seed passed to the bot (noise stream, rollout dice)
  "chosen": "13/10 8/4",                                 // == candidates[0].notation
  "candidates": [                                        // every legal play in the bot's ranking, best first
    { "notation": "13/10 8/4", "equity": 0.179016 },
    …
  ]
}
```

Layout (constants at the top of `bg-bot/examples/gen_decisions.rs`):

- Entries 0–14: the opening position, White on roll, money game, one entry
  per **non-double** roll in `Dice::all()` order (2-1, 3-1, 3-2, 4-1, …,
  6-5); levels cycle beginner, intermediate, club (entry `i` has level
  `i mod 3`), so every level is exercised, including the seeded noise stream
  of the beginner level.
- Entries 15–29: club level, positions sampled along one continuous random
  walk (seed `0xB07_2026_0903`, same walk procedure as `plays.json`, 1–6
  plies between samples): 7 **middlegame** positions (contact, at least 6
  plies into a game), then 4 **race** positions (no contact, at least one
  side not yet all home), then 4 **bear-off** positions (no contact, both
  sides all home). Their match contexts cycle through: money; 7-point match
  3-away/5-away, centred cube; money with the cube on 2 owned by the side on
  roll; Crawford game (5-point match, 1-away/3-away); post-Crawford (5-point
  match, 3-away/1-away); 9-point match 4-away/2-away with the cube on 2 owned
  by the opponent.
- Entry `i` is decided with seed `7 + i`.
- `candidates` holds every legal play, in the order `Bot::choose_play`
  returns them (`bg_bot::rank_plays`). `equity` is the value the play was
  **ranked by**: its search equity (`bg_bot::analysis::value`; 2-ply for the
  club head, 1-ply otherwise), on the match-normalised scale of
  `bg_bot::equity_for` (a single game at the current cube is ±1), rounded to
  six decimals. Rollout statistics are not part of the vector.
- Only the head of the list is comparable: at the club level the top
  `keepTop` (5) candidates are re-scored at 2-ply and sorted among
  themselves; the tail keeps its 1-ply equities in 1-ply order, so a tail
  equity may exceed a head equity. The club head is also rolled out, and a
  rollout re-orders two neighbours only when its gap exceeds twice the
  combined standard error (`bg_bot::search::ranking_gap`; see the module
  docs of `bg-bot/src/search.rs`), so a club head can be out of `equity`
  order at exactly the pairs where that happened. In the committed file this
  occurs once: entry 15, candidates 1 and 2 (`24/21* 13/7` above
  `13/10 10/4`). Beginner and intermediate lists are 1-ply throughout and
  fully sorted. Ties (exact, e.g. several plays that all win or lose with
  certainty) keep the order of the previous stage, down to `legal_plays`
  order; all sorts are stable.
- A roll with no legal move yields the single empty play (`chosen: ""`).

A consumer is correct when, for every entry,
`choosePlay(board, onRoll, dice, match, level, seed)` returns `chosen` and
the same candidate notations in the same order, and each candidate's
`equity` rounds to the listed value. Rust f64 arithmetic is deterministic
across targets; the rounding guards against last-ulp differences in `exp()`
between platform `libm` implementations. The committed file was generated on
macOS and regenerates byte-identically in debug and release there (an
earlier generation also passed byte-for-byte on Linux glibc,
`rust:1.98-slim-bookworm`, aarch64; the current file has not been re-checked
on Linux). The minimum gap between adjacent head equities that are not exact
ties is 3.4e-5 (entry 1, a beginner entry whose noise stream decides a
near-tie between `8/7 6/3` and `6/5 6/3`); `bg-bot/tests/vectors.rs` asserts
that every such gap is either exactly zero or at least 1e-5, ten orders of
magnitude above a last-ulp difference, so an ordering flip from one is not
possible. A decisive-rollout override depends on a gap-versus-2σ
comparison instead; the one in entry 15 is `24/21* 13/7` at a rollout
equity of +0.401 (standard error 0.058) against `13/10 10/4` at +0.109
(0.047): a gap of 0.29 against a threshold of 2 × 0.074 ≈ 0.15, so a
last-ulp difference cannot undo it either.

## Regenerating

```bash
cd engine
cargo run -p bg-core --example gen_vectors -- plays vectors/plays.json
cargo run --release -p bg-bot --example gen_decisions -- decisions vectors/decisions.json   # a few seconds in release, ~25 s in debug
cargo test -p bg-core --test vectors
cargo test --release -p bg-bot --test vectors -- --include-ignored   # full byte-for-byte drift check
```

The two drift tests compare the committed files with the generators' output
byte for byte, so `.gitattributes` in this directory pins `*.json` to LF line
endings (a checkout with `core.autocrlf=true` would otherwise fail the tests
spuriously). The full `decisions.json` comparison is release-only
(`#[ignore]` in the debug profile, where the 20 club-level decisions take
about 25 s); a plain `cargo test -p bg-bot` regenerates and compares every
beginner and intermediate entry plus every fourth club entry, and CI runs the
full comparison in its release step alongside the timing test.

Regenerate only when a rules, notation, evaluator, search or rollout change is
intended; the diff of the affected file is part of the review of that change.
The generators' constants (seeds, counts, gaps) live at the top of
`bg-core/examples/gen_vectors.rs` and `bg-bot/examples/gen_decisions.rs`;
changing them changes every sampled entry.

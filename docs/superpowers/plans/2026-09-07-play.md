# Play Implementation Plan (piece 3)

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development or superpowers:executing-plans. Steps use checkbox syntax.
>
> **Plan format:** interface contracts, data formats, invariants, test oracles and acceptance commands per task (as in the engine plan). Names, props and store shapes below are binding.

**Goal:** A person can open https://backgammon.automated.ink, choose a board theme, start a game against the computer at three levels in single-game or match format, play it on a polished SVG board with the Table layout, see the bot's reasoning and their own move grades in the analysis drawer, and review any finished game move by move. Finished bot games are posted to the server, re-verified by replay, and stored.

**Architecture:** Next.js App Router. The engine runs in a Web Worker (`bg-wasm`, bundler target) so the UI thread never blocks; a typed request/response protocol wraps the worker. Game state lives in a Zustand store fed by the worker; the board is a pure SVG component rendered from an absolute `Board` plus UI-only state (selection, legal targets, animation). Themes are CSS custom property sets on `[data-theme]`. Server: Prisma + Postgres with the `Game`/`GameSeat` tables from the spec; one route handler stores finished bot games after replaying the record with `bg-wasm` in Node.

**Tech Stack:** Next 16.3 (Turbopack), React 19, TypeScript strict, Zustand 5, Tailwind 4 for layout utilities + hand-written CSS tokens for themes, `bg-wasm` (workspace), Prisma 6 + PostgreSQL 16, Vitest 4 (jsdom for components), Playwright (e2e + screenshot matrix), Storybook is NOT used.

**Spec:** `docs/superpowers/specs/2026-09-03-backgammon-platform-design.md` §5.1–5.3, 5.5 (Game/GameSeat only), 7 (web tests), 8.

## Domain and UI conventions (binding)

**Absolute coordinates.** UI always holds an absolute `Board` (`white`/`black` arrays as bg-core serialises). The human is always **White** in bot games and sits at the bottom; White moves 24→1 clockwise from the top-right… precisely: layout is the standard "White bears off bottom-right": bottom row from left shows points 12…7 | bar | 6…1; top row shows 13…18 | bar | 19…24. Bot is Black.

**Point geometry** (`web/src/components/board/geometry.ts`, pure): `viewBox 0 0 1000 700`; frame 24; bar width 60; each half 6 columns; `pointX(p: 1..24) → center x`, `pointBaseY(p)` (top or bottom), `checkerRadius`, `stackOffset(n)` (5 full, then compressed), `barX`, `offTrayX(player)`. Tests assert symmetric columns and that 15 stacked checkers fit within half height.

**Engine worker protocol** (`web/src/engine/protocol.ts`):
```ts
type Req =
 | { id: number; type: 'legalPlays'; board: Board; onRoll: Player; dice: Dice }
 | { id: number; type: 'applyPlay'; board: Board; onRoll: Player; play: Play }
 | { id: number; type: 'choosePlay'; board: Board; onRoll: Player; dice: Dice; matchCtx: MatchContext; level: Level; seed: number }
 | { id: number; type: 'cubeAction'; board: Board; onRoll: Player; matchCtx: MatchContext; level: Level }
 | { id: number; type: 'analyzePlay'; board: Board; onRoll: Player; dice: Dice; matchCtx: MatchContext; played: string; seed: number }
 | { id: number; type: 'replay'; record: Record }
type Res = { id: number; ok: true; result: unknown } | { id: number; ok: false; error: string }
```
`web/src/engine/client.ts` exposes `createEngine(): Engine` with typed async methods and one in-flight queue; a `MockEngine` with the same interface (scripted responses) is used in component tests.

**Game store** (`web/src/game/store.ts`, Zustand):
```ts
interface GameStore {
  match: MatchState | null;            // from engine's GameState/MatchState JSON, kept absolute
  record: Record | null;               // seed + turns, grows as play proceeds
  seatOf: { white: 'human'|'bot'; black: 'human'|'bot' };
  botLevel: Level; theme: ThemeId;     // theme persisted (localStorage key 'bg.theme')
  ui: { selectedFrom: number|null; legalTargets: number[]; pendingMoves: Move[]; busy: boolean; lastError: string|null };
  // actions
  newGame(opts: { format: 'single'|{ matchTo: number }; level: Level; seed?: number }): Promise<void>;
  roll(): Promise<void>; selectPoint(p: number): Promise<void>; undoPending(): void; confirmPlay(): Promise<void>;
  double(): Promise<void>; take(): Promise<void>; drop(): Promise<void>; resign(kind: ResultKind): Promise<void>;
  botTurn(): Promise<void>;            // roll (or cube action) + choosePlay + apply; stores candidates for the drawer
  setTheme(t: ThemeId): void;
}
```
The store never computes rules itself: every legality question goes to the engine. Human move entry: click/drag a checker (`selectPoint(from)`) → engine `legalPlays` filtered by the pending prefix → highlight targets → `selectPoint(to)` appends a `Move`; when the pending sequence completes a legal play (or no further move is possible) `confirmPlay()` applies it. `undoPending()` removes the last pending move. Dice are rolled by the store from `DiceRng`-equivalent in the engine? **No**: for bot games the browser owns the seed: `newGame` picks `seed = crypto.getRandomValues` 53-bit; rolls come from `replay`-compatible ordering by sending the growing `record` to the engine's `replay` and reading `match.game.dice` — simpler: the engine exposes `roll(record) -> { dice, match }`? Not in the API. **Decision:** the worker keeps a `DiceRng` equivalent by calling `replay(record)` after appending a `{ action: 'roll' }` turn: replay derives the dice from the seed deterministically, so the returned `MatchState.game.dice` is the roll. This keeps one source of truth (the record) and makes the server re-verification trivial.

**Themes** (`web/src/styles/themes.css`): `[data-theme="heritage"]` (default), `[data-theme="broadcast"]`, `[data-theme="editorial"]`; tokens: `--board-frame`, `--board-felt`, `--board-bar`, `--point-a`, `--point-b`, `--checker-white`, `--checker-white-edge`, `--checker-black`, `--checker-black-edge`, `--die-face`, `--die-pip`, `--cube-face`, `--cube-text`, `--ui-bg`, `--ui-fg`, `--ui-accent`, `--font-display`, `--radius-board`, `--shadow-checker`. Values from the brainstorm studies (heritage: walnut #2d1a0f/#4a2c1a, felt #1f3a2e, points #c9a86a/#7a1f2b, checkers #fbf3e0/#0f0a08, accent #d9b75a; broadcast: #12141a/#22262e, points #3a4150/#2c313c, checkers #f2f4f7/#141821, accent #f5c542; editorial: #efe6d6/#f7f1e6, points #a9b7a2/#c98b6a, checkers #fffdf8/#23201e, accent #b86a45).

**Routes.** `/` landing with "Play the computer" → `/play/new` (form: format, level, theme preview) → `/play/[gameId]` (local id `local-<seed>` for bot games in this piece) → after finish `/review/[gameId]` (piece E; local games stay in `localStorage` under `bg.games.<id>` until posted). `/health` unchanged.

**Record persistence API** (piece E): `POST /api/games` body `{ record: Record, seats: { white: { kind: 'guest', name }, black: { kind: 'bot', level } } }` → replays with `bg-wasm` in Node; on success stores `Game` (status finished, result, moveLog = record, seed) and returns `{ id }`; 400 with `{ error }` if replay fails or the game is not finished. `GET /api/games/[id]` returns `{ record, result, seats }` for review.

# PR D — engine in the browser, board, bot game

### Task 1: Engine worker + client
Files: `web/src/engine/*`, `web/tests/engine-client.test.ts`. Worker: `import init or the bundler-target module` from `bg-wasm`; handles `Req` → calls the JSON functions → `Res`. Client: promise map by `id`, timeouts (10 s) rejecting with a clear message, `terminate()`. Test with a fake `Worker` (jsdom) exercising ordering, error propagation and timeout. Acceptance: `pnpm --filter web test -- engine-client`, typecheck, `next build` (worker chunk emitted).

### Task 2: Geometry + Board component
Files: `components/board/*`, `styles/themes.css`, `tests/geometry.test.ts`, `tests/components/board.test.tsx`. `Board` props: `{ board: Board; onRoll: Player|null; dice: Dice|null; cube: Cube; selectedFrom: number|null; legalTargets: number[]; pending: Move[]; onPointClick(p: number): void; onBarClick(): void; onOffClick(): void; perspective: 'white' }`. Renders all checkers with `data-testid="checker-<player>-<point>-<index>"`, targets with `data-legal="true"`, stack count badges beyond 5. Keyboard: points are buttons with `aria-label="Point 13, 5 white checkers"`; Tab order along the movement direction. Reduced motion respected. Tests: opening position renders 30 checkers; clicking a legal target calls `onPointClick(to)`; all three themes apply distinct `--board-felt`.

### Task 3: Game store with MockEngine
Files: `game/*`, `tests/store.test.ts`, `tests/record.test.ts`. Implements the store contract; tests script MockEngine responses to cover: newGame → opening roll → human move entry with pending moves and undo → confirm → bot turn → cube offer/take/drop → finish; `record` grows exactly one `Turn` per action; errors surface in `ui.lastError` and never throw to React.

### Task 4: Table layout, player cards, action bar, theme switch
Files: `components/table/*`, `components/theme/*`, `app/play/**`, `styles/*`. `TableLayout` = player cards flanking the board (name, score, pip count from `Board.pip_count` equivalent computed in TS with a test, cube ownership), `ActionBar` (Roll, Undo, Confirm, Double, Take, Drop, Resign; disabled states from store), `StatusLine` ("Your roll: 6-3", "Computer is thinking…"). Mobile: cards become bars above/below the board. Theme switch in the header; persisted; `data-theme` set on `<html>` before first paint via an inline script to avoid flash. `/play/new` form → `/play/local-<seed>`.

### Task 5: Landing page and polish
Files: `app/page.tsx`, `styles/globals.css`. Landing keeps `#board-mount` (a static rendered board in the default theme as hero) and a single primary action "Play the computer"; secondary "Choose your board" opens the theme switch. Typography per theme (`--font-display` serif for heritage/editorial, sans for broadcast). Lighthouse: no CLS from the board (explicit `viewBox` + aspect-ratio).

### Task 6: E2E + gate (PR D)
Files: `web/e2e/bot-game.spec.ts`, `web/e2e/themes.spec.ts`, `ci.yml` (upload screenshots artifact always), README. Bot game e2e: start a 1-point game at beginner with a fixed seed via `?seed=`, play until finished by always choosing the first legal target (a helper reads `data-legal`), assert the finish banner. Screenshot matrix: 3 themes × widths 375/768/1440 of `/play/local-42` at the opening position, stored under `web/test-results/screens/`. Gate: full local gate + `docker build --platform linux/amd64` + smoke.

# PR E — analysis drawer, review, persistence

### Task 7: Analysis drawer
Files: `components/analysis/*`, store additions `analysis: { forBot: MoveAnalysisLike|null; forHuman: MoveAnalysis|null; visible: boolean }`. After each bot move: candidates from `choosePlay` (equity, probs, rollout stats with trials/stdErr) rendered as `CandidateList` with `ProbBar` (win/gammon/backgammon). After each human confirm: `analyzePlay` (Club params) → grade badge (best/fine/error/blunder) with error size; collapsed drawer shows a one-line verdict. Tabs: Analysis · Moves (`MoveList` from `record`) · Chat (placeholder tab, disabled, `(planned)`). Toggle persisted (`bg.analysis`).

### Task 8: Post-game review
Files: `components/review/*`, `app/review/[gameId]/page.tsx`. Step through `record.turns` with ←/→ and a slider; board shows the position before each turn; for move turns show `analyzePlay` lazily (cache per turn index); summary header: counts of errors/blunders per side and total equity lost.

### Task 9: Prisma schema + migrations + verify/store service
Files: `web/prisma/schema.prisma`, `web/prisma/migrations/*`, `web/src/server/{db.ts,games.ts}`, `tests/api-games.test.ts`. Models `Game`, `GameSeat` per spec §5.5 (only these two now). `verifyAndStore(record, seats)`: `bg-wasm` in Node replays; must be finished; computes result; stores. Tests mock Prisma and use a real wasm replay on a fixture record.

### Task 10: API routes, entrypoint migrations, compose env
Files: `app/api/games/route.ts`, `app/api/games/[id]/route.ts`, `web/scripts/docker-entrypoint.sh`, `Dockerfile` (copy prisma + run `prisma migrate deploy` at start; requires `DATABASE_URL`), `deploy/docker-compose.prod.yml` (already passes `DATABASE_URL`). Rate limit: 30 POST/min/IP in-memory. The store posts a finished bot game once (`bg.games.<id>.posted`).

### Task 11: E2E + gate (PR E)
`web/e2e/review.spec.ts`: finish a seeded game, open review, step to a turn, see a grade badge. API e2e via Playwright request against the dev server with a Postgres from `docker compose -f web/docker-compose.dev.yml` (new, dev only). Gate + Docker smoke, and after deploy: `POST /api/games` with an invalid record returns 400 on the live site (manual check by the orchestrator).
